# Phase 5.2: HIPAA / GDPR Compliance — Research

**Researched:** 2026-06-29
**Domain:** Healthcare data compliance — field-level encryption, audit trails, GDPR endpoints, consent, retention
**Confidence:** HIGH (regulatory requirements verified against official GDPR text; encryption patterns verified against npm registry and official docs)

## Summary

MediConnect stores Protected Health Information (PHI) across six models — Patient, ConsultationNote, Prescription, LabResult, Appointment, and User — with **zero encryption at rest** and **no audit trail** beyond ReadEvent (which is scoped only to appointment reads by doctors). This phase closes the gap between the current state and HIPAA/GDPR baseline requirements.

The recommended approach is: **manual AES-256-GCM via Node.js built-in `crypto` module** (not a third-party plugin) wrapped in reusable encrypt/decrypt utility functions, applied via Mongoose pre-save / post-init hooks on a per-field basis. This gives full control over key rotation, migration, and audit behavior without adding external attack surface.

Audit trail is a **new `AuditLog` model** — ReadEvent is too narrow (appointment reads only) and has no IP, userAgent, action type, or resource type fields. ReadEvent stays for its existing UI read-receipt purpose.

GDPR erasure uses **anonymization + selective hard delete**, not full cascade delete, because HIPAA requires medical records to be retained for 6 years. The two regulations are in tension; the anonymization approach satisfies both.

**Primary recommendation:** Encrypt at the service/middleware layer using a thin `fieldEncryption.js` utility, build a comprehensive AuditLog model, implement erasure as anonymization, export as a BullMQ background job (same pattern as reminderWorker), and add consent fields to User at registration.

### Pattern 1: AES-256-GCM Field Encryption Utility

**What:** Thin wrapper around Node.js `crypto` — encrypt returns IV+ciphertext+authTag as a pipe-delimited string; decrypt reverses it. Key is 32-byte hex from env var.

**When to use:** Called in Mongoose pre('save') hook to encrypt, post('init') hook to decrypt.

```javascript
// Source: Node.js crypto docs (https://nodejs.org/api/crypto.html)
// apps/api/src/utils/fieldEncryption.js

const crypto = require('crypto');

const ALGORITHM = 'aes-256-gcm';
const IV_LENGTH = 16;
const AUTH_TAG_LENGTH = 16;

function getKey() {
  const key = process.env.FIELD_ENCRYPTION_KEY;
  if (!key || key.length !== 64) {
    throw new Error('FIELD_ENCRYPTION_KEY must be a 64-char hex string (32 bytes)');
  }
  return Buffer.from(key, 'hex');
}

/**
 * Returns pipe-delimited string: iv|ciphertext|authTag (all hex)
 * Returns null if value is null/undefined — preserves sparse fields
 */
function encrypt(plaintext) {
  if (plaintext == null) return null;
  const iv = crypto.randomBytes(IV_LENGTH);
  const cipher = crypto.createCipheriv(ALGORITHM, getKey(), iv);
  const encrypted = Buffer.concat([cipher.update(String(plaintext), 'utf8'), cipher.final()]);
  const authTag = cipher.getAuthTag();
  return [iv.toString('hex'), encrypted.toString('hex'), authTag.toString('hex')].join('|');
}

/**
 * Decrypts pipe-delimited string back to plaintext string.
 * Returns null for null values.
 * Throws on tampered ciphertext (GCM auth tag mismatch).
 */
function decrypt(ciphertext) {
  if (ciphertext == null) return null;
  // Already plaintext (migration: value has no '|' delimiter)
  if (!ciphertext.includes('|')) return ciphertext;
  const [ivHex, encHex, tagHex] = ciphertext.split('|');
  const decipher = crypto.createDecipheriv(ALGORITHM, getKey(), Buffer.from(ivHex, 'hex'));
  decipher.setAuthTag(Buffer.from(tagHex, 'hex'));
  const decrypted = Buffer.concat([
    decipher.update(Buffer.from(encHex, 'hex')),
    decipher.final(),
  ]);
  return decrypted.toString('utf8');
}

module.exports = { encrypt, decrypt };
```

**Key insight for migration:** The `decrypt` function checks for the `|` delimiter. Existing plaintext records that have never been encrypted do not contain `|` and are returned as-is. This means the migration can be done lazily (encrypt on next save) with no downtime, or eagerly via a one-time migration script.

### Pattern 2: Mongoose Hook Application

```javascript
// Applied to Patient model (example)
// Source: Mongoose docs (https://mongoosejs.com/docs/middleware.html)

const { encrypt, decrypt } = require('../utils/fieldEncryption');

const ENCRYPTED_PATIENT_FIELDS = ['medicalHistory', 'allergies', 'conditions', 'dateOfBirth'];

patientSchema.pre('save', function (next) {
  ENCRYPTED_PATIENT_FIELDS.forEach(field => {
    if (this.isModified(field) && this[field] != null) {
      if (Array.isArray(this[field])) {
        this[field] = this[field].map(v => encrypt(v));
      } else {
        this[field] = encrypt(this[field]);
      }
    }
  });
  next();
});

patientSchema.post('init', function (doc) {
  ENCRYPTED_PATIENT_FIELDS.forEach(field => {
    if (doc[field] != null) {
      if (Array.isArray(doc[field])) {
        doc[field] = doc[field].map(v => decrypt(v));
      } else {
        doc[field] = decrypt(doc[field]);
      }
    }
  });
});
```

**Critical warning:** `post('init')` mutates the in-memory document. `findOneAndUpdate` bypasses `pre('save')` — use `pre('findOneAndUpdate')` hook or switch to `.save()` pattern for encrypted fields.

### Anti-Patterns to Avoid

- **Encrypting MongoDB ObjectIds or indexed fields:** Encryption makes the field unsearchable. Only encrypt PHI content fields, never IDs used in foreign key joins.
- **Using `findOneAndUpdate` on encrypted fields:** Bypasses pre-save hooks; the update arrives at MongoDB unencrypted. Always use find-then-save for encrypted documents.
- **Storing encryption key in code or `.env` committed to git:** Key must be injected at deploy time as an environment secret (Railway/Render env var, or AWS Secrets Manager).
- **Hard-deleting medical records for GDPR erasure:** HIPAA retention of 6 years takes precedence. Anonymize instead.
- **Setting TTL on AuditLog collection:** HIPAA requires 6-year audit log retention; TTL would delete them early.
- **Logging PHI in audit logs:** Audit logs capture WHO accessed WHAT record (by ID), not the PHI content itself.
- **Synchronous audit log writes in request path:** AuditLog.create() should be fire-and-forget (async, no await in middleware) to avoid adding latency to every request.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cryptographically random IVs | Manual random bytes | `crypto.randomBytes(16)` | IV must be cryptographically random; Math.random() is not |
| Auth tag verification | Manual HMAC comparison | AES-256-GCM built-in auth tag | GCM mode automatically detects tampering on decipher.final() |
| Blind index | Custom hash function | HMAC-SHA256 with separate secret key | HMAC is keyed; plain SHA256 is rainbow-table-attackable |
| Retention scheduling | Cron in main process | BullMQ repeatable job (existing pattern) | Main process cron dies on restart; BullMQ job persists in Redis |
| Erasure atomicity | Sequential awaits | MongoDB session transactions | Partial erasure leaves inconsistent state that cannot be undone |

**Key insight:** Do not use `mongoose-field-encryption` (AES-256-CBC, no auth tag). Do not use `mongoose-encryption` (document-level, encrypts entire document making selective field queries impossible). The 30-line custom utility is safer and more auditable.

## GDPR Article 17 — Right to Erasure: Design

### What can be anonymized vs. what must be kept

| Model | Action | Fields to Anonymize | Fields to Keep | Reason |
|-------|--------|--------------------|--------------|----|
| `User` | Anonymize | name → "DELETED", email → uuid@deleted.invalid, googleId → null, fcmToken → null, photoUrl → null | role, _id, timestamps, `erasedAt` flag | _id referenced in other collections |
| `Patient` | Anonymize | medicalHistory → [], allergies → [], conditions → [], dateOfBirth → null, bloodType → null, notes → [], homeLocation → null | _id, userId ref, timestamps | Medical record structure retained for HIPAA |
| `ConsultationNote` | Anonymize content | content → "[ERASED]", aiAssist → cleared | appointmentId, authorId, timestamps | Appointment record integrity |
| `Prescription` | Anonymize | instructions → "[ERASED]", medications[].name → "[ERASED]" | doctorId, patientId, appointmentId, validUntil, timestamps | Drug safety: prescription dates retained |
| `Appointment` | **Keep as-is** | — | all fields | HIPAA — medical encounter records cannot be deleted |
| `LabResult` | Anonymize values | tests[].value → "[ERASED]", notes → "[ERASED]", aiInterpretation → cleared | labName, tests[].name, tests[].flag, patientId, doctorId, timestamps | Abnormal flags retained for safety reference |
| `Message` | Hard delete | all | — | Chat messages are not medical records |
| `SharedLink` | Hard delete | all | — | Tokens must be revoked |
| `Notification` | Hard delete | all | — | No retention value |
| `Report` | Anonymize | reporterId → anonymized | targetId, reason, status, timestamps | Legal/moderation record |

### Blocking Conditions (cannot erase if)

- Pending or confirmed appointments in the future (status: 'pending' or 'confirmed', date > now)
- Active SharedLink tokens not yet expired — must revoke first, then erase

### Erasure Flow (atomic via MongoDB session)

```
POST /api/privacy/erase (patient auth required)
  1. Validate authenticated user is the requesting patient
  2. Check blocking conditions — return 409 if blocked with reason
  3. Begin MongoDB session + startTransaction()
  4. Anonymize User document
  5. Anonymize Patient document
  6. Anonymize all ConsultationNote documents (updateMany)
  7. Anonymize all Prescription documents (updateMany)
  8. Anonymize all LabResult documents (updateMany)
  9. Hard delete Messages (deleteMany)
  10. Hard delete SharedLinks (deleteMany)
  11. Hard delete Notifications (deleteMany)
  12. Set User.erasedAt = new Date()
  13. Commit transaction
  14. Write AuditLog entry (action: 'erase', outcome: 'success')
  15. Invalidate JWT (blacklist or short-exp — see note below)
  16. Return 200
```

**JWT invalidation on erasure:** Existing JWT middleware is stateless. After erasure, add a check: if `User.erasedAt` exists, reject all tokens for that user. This requires one DB lookup per request for erased users — acceptable because erased users become rare and can be cached in Redis with a short TTL.

## GDPR Article 20 — Data Export: Design

### Format

Structured JSON (not PDF) — JSON is machine-readable as required by Article 20. Include a `_metadata` envelope with export timestamp, patient identity, and version.

### Collections to Include

- User (PII: name, email, role, joinedAt — NOT password hash)
- Patient (all fields, decrypted)
- Appointments (all, both as patient)
- ConsultationNote (shared visibility only — private doctor notes are excluded; private notes are the doctor's work product, not the patient's data)
- Prescriptions (all)
- LabResults (all)
- Messages (all, per appointment)
- Reviews written by patient

### Export Flow (background job — same pattern as reminderWorker)

```
POST /api/privacy/export
  1. Enqueue BullMQ export job with { patientId }
  2. Return 202 Accepted with jobId

exportWorker:
  3. Collect all collections (queries by patientId)
  4. Decrypt all encrypted fields in memory
  5. Serialize to JSON
  6. Upload to Cloudinary (or temp signed URL) — NOT stored in MongoDB
  7. Create in-app Notification with download link
  8. Write AuditLog (action: 'export')
  9. Download link expires in 24h (Cloudinary signed URL)
```

**Why background job:** Patient may have years of data across 6+ collections. Synchronous response risks timeout. BullMQ export queue mirrors the existing reminder queue pattern exactly.

**Export file should NOT be encrypted:** The patient is the data subject; they receive their own plaintext data. The transport is HTTPS, which provides encryption in transit.

## Consent Tracking: Design

### Where to store

On the `User` model (not a separate collection). Consent is tied to the identity record and must be atomic with registration.

### Registration flow change

```
POST /api/auth/register
  Body: { name, email, password, role, consentAccepted: true }

  Validation:
    - consentAccepted must be boolean true (not truthy — exact value check)
    - If false or missing: 400 "You must accept the Terms of Service to register"

  On success:
    - Set user.consentVersion = process.env.TERMS_VERSION (e.g., "2024-01")
    - Set user.consentTimestamp = new Date()
    - Set user.consentIp = req.ip (req.ip is trustworthy because app.set('trust proxy', 1) is already set in index.js)
    - Set user.dataProcessingAllowed = true
```

### Re-consent on terms update

When `TERMS_VERSION` env var is bumped, add middleware that checks `user.consentVersion !== currentTermsVersion` and redirects/blocks with a 403 + `{ requiresReconsent: true }` response. The frontend handles showing the new terms modal.

### Consent withdrawal

```
POST /api/privacy/consent/withdraw
  - Sets user.dataProcessingAllowed = false
  - Sets user.consentWithdrawnAt = new Date()
  - Does NOT immediately erase data — triggers a grace period (e.g., 30 days)
  - After grace period, retentionWorker picks it up for erasure
  - Response: 200 with explanation of grace period
```

## Data Retention: Design

### HIPAA minimum

6 years from date of creation or last use. [CITED: https://www.hipaajournal.com/hipaa-retention-requirements/]

### "Inactive" definition

A patient account is inactive when:
- Last login > 7 years ago (adds 1-year buffer over HIPAA minimum)
- AND no appointments with date < 7 years ago
- AND no active prescriptions with validUntil > now

### Implementation

BullMQ repeatable job running daily at 02:00 UTC (same connection as existing reminderQueue):

```javascript
// retentionWorker.js — daily cron
// 1. Find User records where:
//    updatedAt < (now - 7 years)
//    AND role === 'patient'
//    AND erasedAt is null
// 2. For each candidate: verify no active appointments
// 3. Enqueue erasure job (reuses erasureService.js)
// 4. Write AuditLog (action: 'delete', meta: { reason: 'retention_policy' })
```

### Soft delete vs. hard delete

Soft delete for User (set `erasedAt`, keep `_id` for referential integrity). Hard delete for Messages, Notifications, SharedLinks (no medical value). Anonymize all PHI fields on Patient, ConsultationNote, Prescription, LabResult (HIPAA-compliant — structure retained, values erased).

## Key Management

### Decision: Environment variable master key (pragmatic for current stack)

**Why not AWS KMS or HashiCorp Vault for this phase:** Both require additional infrastructure (AWS account with KMS configured, or a separate Vault cluster). For a phase focused on compliance foundations, the operational complexity of external KMS outweighs the benefit at this scale. The pragmatic choice is a 256-bit key stored as a Railway/Render environment secret.

**Key generation:**
```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

**Required env vars:**
```
FIELD_ENCRYPTION_KEY=<64-char hex>     # AES-256-GCM key for PHI fields
BLIND_INDEX_KEY=<64-char hex>          # Separate key for HMAC blind indexes
TERMS_VERSION=2024-01                  # Current terms version for re-consent checks
```

**Key rotation path (future):** When key rotation is needed, add a `keyVersion` field to encrypted strings (e.g., `v1|iv|ciphertext|tag`). Re-encryption migration script decrypts with old key, re-encrypts with new key. This is NOT in scope for Phase 5.2 but the `|` delimiter format supports it.

**Risk of env-var approach:** If the key leaks (via logging, error messages, or env var exposure), all encrypted fields are compromised retroactively. Mitigation: ensure the key is never logged (add `FIELD_ENCRYPTION_KEY` to log scrubbing list), rotate immediately if exposed.

## Migration Strategy for Existing Plaintext Records

### Approach: Lazy migration + eager one-time script (two-phase)

**Phase A (lazy — immediate, zero downtime):**
- Deploy updated Mongoose hooks
- Existing plaintext records are returned as-is on read (the `decrypt` function checks for `|` delimiter; absence means plaintext)
- On next save of any record, the `pre('save')` hook encrypts it
- Over time, active records get encrypted organically

**Phase B (eager — run after Phase A is stable):**
- One-time migration script: `scripts/migrateEncryption.js`
- Iterates in batches of 100 using cursor-based pagination
- For each document: decrypt (returns plaintext because no `|`), encrypt, save
- Script is idempotent: if a field already has `|`, skip it
- Run during low-traffic window
- Log progress to stdout for operator visibility

```javascript
// scripts/migrateEncryption.js (pseudocode — actual implementation is a plan task)
const cursor = Patient.find({ 'medicalHistory.0': { $exists: true } }).cursor();
for await (const doc of cursor) {
  const needsMigration = doc.medicalHistory.some(v => !v.includes('|'));
  if (needsMigration) {
    // pre('save') hook will encrypt on next save
    await doc.save();
  }
}
```

**Downtime risk: NONE.** The lazy decrypt path handles mixed-state documents transparently. Both encrypted and plaintext values are handled correctly by the same `decrypt` function.

## Common Pitfalls

### Pitfall 1: `findOneAndUpdate` Bypasses Encryption Hooks

**What goes wrong:** Routes that update patient data using `Model.findOneAndUpdate(...)` or `Model.updateMany(...)` bypass the `pre('save')` hook. The update is written to MongoDB in plaintext even though other records are encrypted.

**Why it happens:** Mongoose `pre('save')` only fires on `.save()`. Query-level update methods bypass document middleware.

**How to avoid:** For any field that is encrypted, switch from `findOneAndUpdate` to `findById` + mutate + `.save()`. For bulk anonymization in erasure, use `pre('findOneAndUpdate')` hooks or handle encryption explicitly in the service layer.

**Warning signs:** Encrypted fields stored without `|` delimiter in MongoDB (inspect via mongo shell).

### Pitfall 2: Querying on Encrypted Fields

**What goes wrong:** Code tries to `Patient.findOne({ medicalHistory: 'diabetes' })` after encryption. Returns no results because the stored value is ciphertext.

**Why it happens:** AES-256-GCM with random IV produces different ciphertext each time. No two encrypted values match.

**How to avoid:** Never query by the content of encrypted fields. Query by `patientId`, `doctorId`, `appointmentId` (unencrypted IDs), then decrypt in memory. For `User.email` login lookup, implement blind index (HMAC hash stored in `emailHash` field).

**Warning signs:** Login stop working, doctor search returns empty results.

### Pitfall 3: Audit Log PHI Leakage

**What goes wrong:** Audit log entries include the actual PHI value in the `meta` field — e.g., `{ meta: { content: "patient has HIV" } }`.

**Why it happens:** Developers add context to audit logs for debugging convenience.

**How to avoid:** Audit logs capture resource type and resource ID only, never content. The auditor uses the ID to look up the actual record. Document this rule explicitly in the auditLog middleware.

### Pitfall 4: GDPR Erasure Partial Failure

**What goes wrong:** Erasure anonymizes User but fails on ConsultationNote update (e.g., MongoDB timeout). User is marked erased but notes still contain PHI.

**Why it happens:** Sequential awaits without transaction — partial state committed.

**How to avoid:** Use MongoDB session transactions for the entire erasure flow. If MongoDB replica set is not configured (standalone dev instance), document that transactions require a replica set or use MongoDB Atlas (which always has replica sets). Add a rollback-capable service method.

**Warning signs:** `erasedAt` is set on User but `Patient.medicalHistory` still contains data.

### Pitfall 5: Encryption Key in Error Messages / Logs

**What goes wrong:** An `Error('Invalid key: ' + key)` in `fieldEncryption.js` logs the encryption key to stdout.

**Why it happens:** Debug-first development patterns.

**How to avoid:** The encryption utility must NEVER log or include the key value in error messages. Throw generic errors: `throw new Error('Encryption configuration error')`.

### Pitfall 6: AuditLog Writes Blocking Request Performance

**What goes wrong:** Every API request awaits `AuditLog.create()` — adds 10-30ms of DB write latency to every PHI endpoint.

**Why it happens:** `await auditLog.create(...)` in middleware.

**How to avoid:** Fire-and-forget: `AuditLog.create({...}).catch(err => console.error('[audit]', err.message))` — no await. Accept that a small number of audit writes may be lost under extreme DB pressure (acceptable tradeoff vs. blocking every request).

## Implementation Risks

| Risk | Severity | Mitigation |
|------|----------|-----------|
| Encrypting fields that are searched by value | HIGH — breaks queries silently | Audit all `Model.find({ encryptedField: value })` before deploying hooks |
| `findOneAndUpdate` bypasses hooks | HIGH — plaintext written to DB | Grep all routes for `findOneAndUpdate` on encrypted models; refactor to save() |

| Encryption key loss = permanent data loss | CRITICAL | Back up `FIELD_ENCRYPTION_KEY` to a second secure location immediately after generation |

| GDPR erasure doesn't revoke active sessions | MEDIUM — erased user's JWT still valid until expiry | Add `erasedAt` check in auth.js middleware |
| Retention cron double-run | LOW — BullMQ repeatable jobs are idempotent by job name | Erasure service is idempotent: re-erasing already-erased records is a no-op |

## Open Questions

1. **PDPL (Saudi Arabia) vs. HIPAA/GDPR**
   - The ROADMAP mentions PDPL (Saudi Arabia) in Phase 7.5. PDPL has different retention periods and consent requirements than GDPR.
   - What we know: Phase 5.2 targets HIPAA (US) + GDPR (EU).
   - Recommendation: Proceed with HIPAA/GDPR only. Flag PDPL as a Phase 7 concern.

2. **MongoDB Replica Set in Development**
   - What we know: Erasure uses transactions; transactions require replica set.
   - What's unclear: Whether the dev environment runs standalone MongoDB or a replica set.
   - Recommendation: Add replica set setup instructions to Wave 0. Alternatively, implement erasure as a sequential compensating transaction (not a MongoDB session) and document the failure mode.

3. **Private Note Exclusion from GDPR Export**
   - What we know: ConsultationNote has `visibility: 'private'` for doctor-only notes.
   - What's unclear: Under GDPR, are doctor's private clinical notes about a patient considered the patient's personal data?
   - Recommendation: [ASSUMED] Include only shared notes in export until legal review confirms. Flag for human decision.

4. **Grace Period Length for Consent Withdrawal**
   - What we know: GDPR does not specify a grace period.
   - What's unclear: Business decision — 30 days? 90 days?
   - Recommendation: Default to 30 days; make it a `CONSENT_WITHDRAWAL_GRACE_DAYS` env var.

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Patient requests erasure of another patient | Tampering / EoP | Verify `req.user.id === patientId` in erasure endpoint before processing |
| Export link stolen after generation | Info Disclosure | Cloudinary signed URL with 24h expiry; link in notification (not in API response) |
| Audit log poisoning (actor logs false events) | Tampering | AuditLog writes are server-side only; no client-supplied action/actor fields |
| Encryption key logged in exception | Info Disclosure | Never include key in error messages; `FIELD_ENCRYPTION_KEY` must be scrubbed from logs |
| Consent bypass on registration | EoP | Server-side validation: `consentAccepted !== true` → 400, never default to true |
| Race condition: two concurrent erasure requests | Tampering | MongoDB findOneAndUpdate with `erasedAt: null` filter as atomic gate; second request finds already-erased record |
