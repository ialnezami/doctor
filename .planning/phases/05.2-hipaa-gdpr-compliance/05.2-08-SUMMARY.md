# Phase 5.2 Plan 08: GDPR Article 20 Data Portability Export — Summary

GDPR Article 20 data export implemented as a BullMQ background job: patient requests export via POST, worker collects and decrypts PHI across 6+ collections, uploads JSON to Cloudinary, and notifies patient via in-app notification with 24h conceptual expiry on the link.

## What Was Built

**`getExportQueue()`** — singleton BullMQ Queue for `gdpr-data-export`, added to `reminderQueue.js` alongside existing queue factories. Exported in `module.exports`.

**`exportWorker.js`** — BullMQ worker that:
1. Loads User profile (password excluded via `-password` select + explicit `delete`)
2. Hydrates Patient, ConsultationNotes (shared only), Prescriptions, LabResults via `.toObject()` to trigger post-init decrypt hooks — `.lean()` deliberately avoided for encrypted PHI models
3. Loads Appointments (lean, no encryption) with doctor name/specialty populated
4. Loads Reviews via `safeRequireModel` (optional model guard)
5. Assembles JSON with `_metadata` envelope (exportedAt, version, dataSubject, generatedBy)
6. Uploads to Cloudinary as `resource_type: 'raw'` JSON file
7. Creates `gdpr_export_ready` Notification with download URL
8. Writes AuditLog entry fire-and-forget (audit failure does not fail the export)

**Two new routes in `privacy.js`:**
- `POST /api/privacy/export` — patient-only; enqueues job, logs audit entry, returns 202 + jobId
- `GET /api/privacy/export/:jobId` — patient-only; ownership check before queue lookup; returns BullMQ state (waiting/active/completed/failed)

**`startExportWorker()`** registered in `index.js` under `REDIS_URL` guard, concurrency=2.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `uploadBuffer()` signature incompatible with export use case**
- Found during: Task 1
- Issue: `cloudinary.js` `uploadBuffer(buffer, folder)` returned `result.secure_url` (string), was hardcoded to `resource_type: 'image'` with image crop transforms. Export worker needed `resource_type: 'raw'` and the full result object (for `public_id` in audit log).
- Fix: Extended to `uploadBuffer(buffer, folder, opts = {})`. Merges opts over defaults; strips `transformation` when `resource_type: 'raw'`. Now returns full Cloudinary result object.
- Callers fixed: `doctors.js` and `patients.js` updated to use `uploadResult.secure_url`.
- Files: `apps/api/src/utils/cloudinary.js`, `apps/api/src/routes/doctors.js`, `apps/api/src/routes/patients.js`
- Commits: 62e7e6c

**2. [Rule 2 - Missing critical functionality] `gdpr_export_ready` not in Notification.type enum**
- Found during: Task 1
- Issue: Notification model `type` field has a strict enum. Creating a notification with type `gdpr_export_ready` would throw a Mongoose ValidationError at runtime, silently failing the export job.
- Fix: Added `'gdpr_export_ready'` to the enum array.
- Files: `apps/api/src/models/Notification.js`
- Commit: 62e7e6c

## Security Considerations

- Password hash never reaches export: excluded via `.select('-password')` AND explicit `delete profileExport.password` (belt-and-suspenders)
- Download URL not returned in API response body — delivered only via encrypted in-app Notification
- Ownership enforced on status endpoint before any queue interaction
- PHI decrypted at time of export (patient is the data subject); Cloudinary URL expires conceptually in 24h
- AuditLog records every export request (enqueue) and every completion
