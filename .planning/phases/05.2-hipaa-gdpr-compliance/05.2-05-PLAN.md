## Objective

Two distinct changes to the auth layer:

1. **Registration consent gate** — `POST /api/auth/register` must reject requests without explicit `consentAccepted: true`. This is GDPR Article 7 — consent must be freely given, specific, and unambiguous. Pre-ticked checkboxes or absent fields are not consent.

2. **Login emailHash switch** — After Plan 02 added `emailHash` to User model and Plan 03 deployed encryption hooks, the login route must switch from `User.findOne({ email })` to `User.findOne({ emailHash })`. The existing `email` field will be encrypted in the migration (Plan 10); once encrypted, `findOne({ email: plaintext })` will never match because stored values are ciphertext.

3. **Erased user JWT invalidation** — After GDPR erasure (Plan 07), the user's JWT is still valid until expiry. The auth middleware must check `erasedAt` on the DB record and reject tokens for erased users.

Purpose: Without the emailHash switch, login will break when the migration script encrypts email values. Deploying the switch before migration ensures login works correctly throughout.

Output: Updated `apps/api/src/routes/auth.js` and `apps/api/src/middleware/auth.js`.

<read_first>

<action>
Modify `apps/api/src/middleware/auth.js` to add a DB check for `erasedAt` after JWT verification. This prevents erased users from accessing any endpoint with their pre-erasure JWTs.

```javascript
'use strict';
const { verify } = require('../utils/jwt');
const User = require('../models/User');

module.exports = async (req, res, next) => {
  const header = req.headers.authorization;
  if (!header?.startsWith('Bearer ')) return res.status(401).json({ message: 'No token' });

  let decoded;
  try {
    decoded = verify(header.slice(7));
  } catch {
    return res.status(401).json({ message: 'Invalid token' });
  }

  req.user = decoded;

  // GDPR erasure check: erased users' tokens must be rejected immediately.
  // This adds one lightweight DB lookup per request for any user whose account
  // has been erased. In practice, erased users are rare — this is acceptable.
  // Future optimization: cache erasedAt status in Redis with short TTL.
  try {
    const user = await User.findById(decoded.id).select('erasedAt isSuspended').lean();
    if (!user) return res.status(401).json({ message: 'User not found' });
    if (user.erasedAt) return res.status(401).json({ message: 'Account has been erased' });
    // isSuspended check was previously only in the login route; add here for global enforcement
    if (user.isSuspended) return res.status(403).json({ message: 'Account suspended. Contact support.' });
  } catch (err) {
    // If DB is down, fail-open is a security risk; fail-closed is safer
    console.error('[auth] DB check failed:', err.message);
    return res.status(503).json({ message: 'Service temporarily unavailable' });
  }

  next();
};
```

IMPORTANT: This adds a DB round-trip to every authenticated request. The `.lean()` option makes the query lightweight (returns plain JS object, no Mongoose overhead). The `select('erasedAt isSuspended')` limits the fields fetched.

The `isSuspended` check migration: This check already existed in the login route. Moving it to the middleware means suspended users are blocked on every request, not just at login. This is strictly more secure — no behavior regression.
